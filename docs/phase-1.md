## Migration command reference

```bash
# Start just the database (Postgres) from the compose stack
docker compose up -d db

# Apply all migrations (create/upgrade the schema)
cd backend && uv run alembic upgrade head

# After changing models: generate a new migration by diffing models vs the live DB
uv run alembic revision --autogenerate -m "describe change"
#   → review the generated file in migrations/versions/ before applying!

# Verify models and DB are in sync (fails if a migration is missing)
uv run alembic check

# Roll back one migration / inspect history
uv run alembic downgrade -1
uv run alembic history --verbose
uv run alembic current
```

### Reset the database from scratch (dev only)
```bash
docker compose down -v      # drops the Postgres volume (all data!)
docker compose up -d db
cd backend && uv run alembic upgrade head
```

## Why Alembic (not `create_all`)
`Base.metadata.create_all()` is fine for a throwaway script but can't evolve a schema
in production — it never issues `ALTER`. Alembic gives us **versioned, reviewable,
reversible** migrations: every schema change is a file in git, applied in order, and
`alembic check` guarantees the models and migrations never silently diverge.
